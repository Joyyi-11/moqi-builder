# Diagnose 模式

## 审计顺序

1. 入口和链接是否真实可用。
2. 文件职责是否越界。
3. 内容是否重复、冲突或过期。
4. 条件路由能否触发全部现有 references；路由指向的文件是否都存在。
5. 跨会话知识是否落在该落的位置。
6. MSA 是否只保留协作必需信息。
7. `ALIGNMENT.md` 是否形成更新、验证和清理闭环。

## 文件检查

### `AGENTS.md`

- 是否能独立约束关键行为和红线？
- 是否定义了启动自检（真实源标记、核心文件到位、指令生效），把加载失败从静默变可见？
- 是否包含日常识别跨会话变化、主动提议、用户确认后更新真实源的共同维护闭环？
- 是否混入平台版本、完整工作流、历史叙事或个人履历？
- 是否混入会过期的「当前状态」类内容（此刻有几条、某版是谁、具体数值口径）？这类内容应下沉到项目文档或数据源。
- 是否为每个现有 reference 提供明确且唯一的触发条件？路由指向的文件是否都真实存在？

### `Memory.md`

- 每条事实是否仍会改变当前协作？
- 动态数字、完整经历和工具清单是否应改为外部资料指针？
- 是否存在“正在”“最近”等已经失效的相对状态？

### `Soul.md`

- 每个模式是否有多个真实场景支撑？
- 是否混入运行规则、系统设计、临时观察或待办？

### `Agent.md`

- 是否只描述协作关系、主动程度、纠错和分歧处理？
- 是否复制入口规则、文件索引、工具清单或维护流程？

### references 和 `ALIGNMENT.md`

- 每个 reference 是否确有重复任务场景，且只按需加载？
- 没有 reference 的用户是否被强行生成了通用技术细则？
- `ALIGNMENT.md` 是否包含基线、分流、去重、Gotchas、验证和提交边界？
- Gotchas 是否仍有真实原因、纠正动作和退出条件？是否有长期未回看的条目（读取时核对机制是否在用）？

### 知识落点与平台载体

- 跨会话知识是否被写进了某个 Agent 的私有记忆？其他 Agent 读不到即视为没写。
- 每个 Agent 的用户级载体是否只记录本平台的加载方式、本机特有的坑与启动指针？出现通用规则副本即为越界，除非有机械校验比对两处一致。
- 项目级的坑与规则是否落在项目文件（就近 `AGENTS.md`）里，而不是只留在某次会话或某个 Agent 的记忆中？

## 输出

按风险排序给出文件、证据、正确归属和具体处理方式。区分“必须修复”“建议精简”“需要用户确认”。诊断模式不自动修改文件。
